# Investigate - 調査と issue への書き戻し

調査の結論は会話の中に置き去りにせず、GitHub issue に書き戻して初めて完了とする。「結果を issue にコメントして」を毎回言わせない。

## 手順

### 1. 引数解析と文脈収集

- `$ARGUMENTS` から issue（URL / `#番号`）と調査テーマを抽出する
- issue の指定がなければ調査テーマだけで開始してよいが、**書き戻し先が無い旨をこの時点でユーザーに伝え、報告時に投稿先を確認する**
- issue 本文と既存コメントを読み、既に判明していること・過去の調査結果と重複しないかを確認する

```bash
gh issue view {番号} --json title,body,url
gh api repos/{owner}/{repo}/issues/{番号}/comments --paginate --jq '.[] | {user: .user.login, body: .body[0:300], created_at}'
```

### 2. 調査の実施

- **事実と推測を分離する**。事実には必ず根拠を付ける: ファイルパス + 行番号、コミット SHA、実行したコマンドとその出力、参照 URL
- コードは実際に読む。ログ・メトリクスは実際に取得する。憶測で埋めない
- 調査中に判明した「調査テーマ外だが重要な発見」は別枠で記録する（本題と混ぜない）
- 破壊的・課金を伴う調査操作（リソースの起動・resume 等）は対象リポジトリの CLAUDE.md の制約に従い、必要なら先にユーザーに確認する

### 3. レポートとユーザー承認

- グローバルのコミュニケーションルールに従い、調査結果を HTML レポート（目的 / 事実 / 根拠 / 結論・推奨アクション）として書き出して提示する。軽微な調査（数行で言い切れるもの）はコンソールで直接提示してよい
- あわせて **issue へ投稿するコメント案** を提示し、承認を得る。承認前に投稿しない

### 4. issue コメントの投稿

コメントは第三者が後から読んで文脈が再現できる形にする:

```markdown
## 調査: {テーマ}

### 背景

{なぜ調べたか 1〜2 行}

### 事実

- {事実} （根拠: {file:line / SHA / コマンド出力 / URL}）

### 結論

{言い切れる結論。言い切れない場合は残る不確実性を明記}

### 推奨アクション / 次のステップ

- {あれば}
```

- 本文はターミナルから直接組み立てず、一時ファイル経由で投稿する（`@` や制御文字による破損を防ぐ）:

```bash
gh issue comment {番号} --body-file /tmp/investigate-comment.md
```

### 5. 完了報告

投稿したコメントの URL を報告する。調査から派生した新しい課題があれば、issue 化の要否をユーザーに提案する。
