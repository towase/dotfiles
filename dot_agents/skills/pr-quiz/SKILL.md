# pr-quiz: PR を出す前の理解度クイズ

AI が書いた変更をレビューに出す前に、作者（ユーザー）がその変更の仕様と技術を自分の言葉で説明できるかを確かめる。クイズに答えるのはユーザーで、Claude は出題者と採点者に徹する。Claude が答えを先回りしたり採点を甘くしたりすると、このスキルは存在意義を失う。

PR の open を機械的に止める仕組みは持たず、Claude が勝手に起動することもない。ユーザーが PR を出す前に `/pr-quiz` で呼び、全問正解したら通常の PR の流れに戻る。

## 手順

### 0. 引数と前提

- `--base <branch>`: 比較元ブランチ。省略時は、既に PR（draft）があればその base、無ければリポジトリの規約（CLAUDE.md / AGENTS.md / memory）、それも無ければ `gh repo view --json defaultBranchRef`
- `--count N`: 問題数。省略時は差分の大きさで決める（「問題数」を参照）
- `--strict`: 1 問でも間違えたらそのセットは不合格にし、新しいセットで最初からやり直す。省略時は「間違えた論点だけ、別の問題で再挑戦」
- 未コミットの変更があれば先に commit してもらう。出題の根拠と diff がずれるのを防ぐため
- ユーザーがクイズを不要と明示したら、出題せずにその旨を伝えて終える

### 1. 材料を集める

出題の根拠になるものをすべて読む。読まずに出した問題は、意図を外すか diff をなぞるだけになる。

```bash
git log --oneline <base>..HEAD
git diff <base>...HEAD --stat
git diff <base>...HEAD
gh pr view --json number,title,body,baseRefName 2>/dev/null   # draft PR があれば
gh issue view <番号> --json title,body --comments               # ブランチ名・commit・PR 本文に #番号 があれば
```

- 変更が触れている仕様書・README・ADR・PR テンプレートがあれば読む
- 変更の周辺コード（呼び出し元・呼び出し先・既存テスト）も見る。「なぜここを変えたか」「何を変えなかったか」は diff の外にある

### 2. 問題を先に書き出す（採点基準を固定する）

出題する前に、全問題と模範解答を `$(bash <skill dir>/scripts/quiz-dir.sh)/quiz-<YYYYMMDD-HHMMSS>.json` に書く。採点基準を先に固定しておかないと、ユーザーの回答を見てから「それも正解にしよう」と流される。記録先は `~/.agents/pr-quiz/<owner>/<repo>/<branch>/` で、後から復習できる。

```json
{
  "branch": "feat/123-foo",
  "head_sha": "abc1234...",
  "base": "main",
  "questions": [
    {
      "id": 1,
      "category": "仕様",
      "question": "この PR の後、未ログインのユーザーが /export を開くと何が起きますか。変更前との違いも含めて答えてください。",
      "model_answer": "ログイン画面へリダイレクトし、戻り先として /export を保持する。変更前は 500 エラーだった。",
      "key_points": ["ログイン画面へリダイレクト", "戻り先を保持", "変更前は 500"],
      "source": ["src/routes/export.ts:12-30", "issue #123 受け入れ条件 2"]
    }
  ],
  "attempts": []
}
```

- `key_points` は「これが言えていれば正解」の必須要素。3 個前後。言い回しは問わないが、要素が欠けたら不正解
- `source` は、間違えたときの解説で指す場所

#### 問題の作り方

目安は仕様 4 割・技術 6 割。「diff を見ただけでは答えられず、意図を理解していれば答えられる」水準を狙う。

仕様の問い（何を・なぜ）

- この変更の後、ユーザーから見える挙動はどう変わるか
- この変更が必要になった背景、issue の達成条件は何か
- 境界・異常系（空・上限・権限なし・二重実行）のとき、どう振る舞う仕様か
- 意図的にスコープ外にしたものと、その理由

技術の問い（どう・なぜその方法）

- この挙動を実現している主要な関数・経路はどこで、データはどう流れるか
- なぜ A ではなく B の方法を取ったか。A だと何が困るか
- X を変える（削る・順番を入れ替える）と何が壊れるか。何がその契約を守っているか
- どのテストが何を守っているか。守れていない穴はどこか
- 移行・互換性・性能・設定で、デプロイ時に気をつけることは何か

避ける問い

- 行番号・変数名・ファイル名の暗記
- はい / いいえで答えられるもの
- 問題文に答えが含まれているもの
- 材料に根拠が無く、Claude の推測でしか答えられないもの

#### 問題数

| 差分 | 問題数 |
|------|------|
| 50 行未満、かつ 1〜2 ファイル | 3 |
| 標準 | 5 |
| 500 行超、または 10 ファイル超 | 7 |

`--count` があればそれに従う。

### 3. 1 問ずつ出題する

- 1 メッセージに 1 問。進捗を添える（例: `問 2/5（技術）`）
- 推奨回答やヒントは出さない。[[walk-points]] とは違い、これは確認ではなく試験
- ユーザーの回答を待つ。待たずに次の問題や解説を出さない
- 「答えを教えて」「わからない」は不正解として扱い、解説してから同じ論点の別の問題を出す

### 4. 採点

- `key_points` の必須要素がすべて含まれていれば正解。言い回し・順序・粒度の違いは問わない
- 要素が欠けている、または「適切に処理する」のように具体性が無い回答は不正解。どの要素が欠けたかを示す
- 正解でも、模範解答に無い補足をユーザーがしていたら、それが正しいかを確認して一言返す
- 不正解のときは次の順で進める
  1. 正解と根拠（`source`）を示して解説する
  2. 同じ論点を別の角度から問う新しい問題を作り、quiz ファイルに追記してから出題する。同じ問題文は繰り返さない（暗記で通ってしまう）
  3. `--strict` のときは、そこでセット全体を不合格にし、新しいセットを作って問 1 からやり直す
- 回答と判定は都度 `attempts` に追記する

### 5. 結果を示して PR の流れに戻る

- 全問正解したら、結果を表にして示す（問・分類・結果・試行回数）
- 間違えた論点は PR 本文やコメントに書き残す価値があるので、提案する
- 以降は通常の PR open の流れに戻る

## やらないこと

- ユーザーの代わりに答える。答えを書いた上で「これで合っていますか」と聞く
- 採点基準を回答を見てから緩める（`key_points` を書く前に出題しない）
- PR の open を止める。このスキルは出題と採点だけを担う
- draft PR の作成に割り込む。draft は CI を回すために先に作ってよい
