# PBT で強化する

PBT（Property-Based Testing）は、入力を自動で大量に作り、どの入力でも成り立つ性質を確かめるテスト。例ベースのテストが選んだ数個の入力の外にある変異を検出できる。SKILL.md 手順 4 で「入力の不足」に分けた変異に使う。

## PBT を使うか決める

次の 2 つが両方そろえば PBT にする。そろわなければ、境界の値を並べた例ベースのテストにする。

- 入力の範囲を言葉で書ける（「4 桁の年と 1〜12 の月を `-` でつないだ文字列」など）
- 実装を見ずに、仕様から性質を言える

## 性質の見つけ方

| 型 | 性質 | 例 |
|------|------|------|
| 往復 | 変換して戻すと元に戻る | 整形してパースすると同じ日付になる |
| 不変条件 | 出力がいつも満たす条件 | ソートの結果は昇順で、要素の集まりは入力と同じ |
| 冪等 | 2 回かけても 1 回と同じ | 正規化、重複の除去 |
| 別の実装との比較 | 遅いが明らかに正しい実装と結果が同じ | 二分探索と線形探索 |
| 入力の変化と出力の関係 | 入力をこう変えると、出力はこう変わる | 月を 1 つ進めて 1 つ戻すと元の月になる。絞り込みの条件を足すと件数は増えない |
| 不正な入力を拒む | 形式の外の入力は受け付けない | 有効な月の前後に文字を足すと、月として扱わない |
| 引数を書き換えない | 呼んだあとも引数が変わらない | 並べ替えの前の `slice()` を消す変異を検出する |

## 入力の作り方

- 有効な入力は `map` で組み立てる。`filter` で捨てると生成が遅くなり、境界の近くに届きにくい
- 入力の範囲は仕様が受け付ける範囲に合わせる。狭すぎると変異を検出できない（月を 1〜11 に限ると、`month <= 12` を `month < 12` にする変異を検出できない）。広げすぎて仕様の外の入力まで作らない
- SKILL.md 手順 4 で見つけた、結果が変わる入力（境界の値）は、fast-check の `examples` に入れて毎回試す。ランダムな生成だけに任せると、実行ごとに検出が揺れる。固定の例を入れる仕組みが無いライブラリ（Go の `testing/quick` など）では、境界の値を例ベースのテストに入れる
- 失敗すると、fast-check は最小化した反例と seed を出す。反例は例ベースのテストとしても残してよい

## 検出を確かめる

再実行で変異が Killed になったら、反例を見る。Stryker モードは `statusReason`（`<workdir>/round-<N>.json`）、手動モードはテストの失敗の出力に出る。反例が仕様の区別しない違い（`-0` と `0` など）や仕様の外の入力だけなら、意味のある検出ではない。性質か入力の範囲を見直すか、その変異を SKILL.md 手順 4 の基準で「許容」に決め直す。

## やってはいけない

- テスト対象と同じ計算を書き写して期待値にする。実装のバグも一緒に写る
- 変異で変わる定数を本番コードから import して期待値にする。定数を変える変異が生き残る
- 時刻・乱数・ネットワークのような、実行ごとに変わるものを性質の中で使う
- 速くするために試行回数（fast-check の `numRuns`、既定 100）を減らす

## ライブラリ

PBT のライブラリは既にリポジトリにあるものを使う。無ければ、どの変異のために要るかを示して、足してよいかをユーザーに聞く。PBT の無いリポジトリに初めて持ち込むときは、標準ライブラリでも先に聞く。その言語に定番のライブラリが無いときや、別の言語のテストを持ち込むことになるときは、聞かずに例ベースにする。

| 言語 | ライブラリ | 備考 |
|------|------|------|
| TS/JS | fast-check | `npm i -D fast-check`。入れたあとは Stryker の `install` をやり直す（references/stryker.md） |
| Kotlin / Java | kotest-property、jqwik | テストの枠組み（kotest か JUnit 5）に合わせる |
| Go | `testing/quick`（標準）、`pgregory.net/rapid` | |
| Python | Hypothesis | |
| PHP | 定番は無い | 聞かずに例ベース。データプロバイダで境界の値を並べる |
| シェル・awk | 定番は無い | 聞かずに例ベース。境界の入力をテストのケースとして並べる |

## 例

kizami の `public/lib/months.js` では、正規表現 `/^(\d{4})-(\d{2})$/` から `^` と `$` を外した変異が生き残った。既存のテストは、前後に余計な文字が付いた入力を使っていなかった。次の性質テストを足すと、2 つとも検出できた。

```ts
import assert from "node:assert/strict";
import fc from "fast-check";
import { test } from "vitest";

import { isMonthValue } from "../public/lib/months.js";

const validMonth = fc
  .tuple(fc.integer({ min: 1000, max: 9999 }), fc.integer({ min: 1, max: 12 }))
  .map(([y, m]) => `${y}-${String(m).padStart(2, "0")}`);

test("有効な月の前後に文字が付いたら月として扱わない", () => {
  fc.assert(
    fc.property(validMonth, fc.string({ minLength: 1 }), (month, extra) => {
      assert.equal(isMonthValue(month), true);
      assert.equal(isMonthValue(extra + month), false);
      assert.equal(isMonthValue(month + extra), false);
    }),
  );
});
```

同じファイルの `value ?? ""` の `""` を別の文字列に変える変異は、どちらの文字列も正規表現に一致せず `false` を返すので、等価変異として扱った。
