# mutation-check: 変異テストでテストの検出力を測り、強化する

本番コードにわざと小さなバグ（変異）を入れ、テストがそれを検出できるかで、テストの検出力を測る。カバレッジは「その行を通ったか」しか見ないが、変異テストは「結果を確かめているか」まで見る。AI が書いたテストは、行を通るだけで期待値を確かめていなかったり、境界の入力が抜けていたりしやすい。

生き残った変異はテストの穴の場所を示す。穴は例ベースのテストか PBT（Property-Based Testing）で埋め、同じ範囲で再実行して埋まったことを確かめる。目的はバグを検出できるテストにすることで、スコアを上げることではない。スコアのためにテストや設定を細工すると、このスキルは存在意義を失う（「不正防止のルール」）。

## 起動

- 自動: プロダクトの実装のテストを書いた・変えたら、そのテストが通ったところで、commit の前にユーザーに聞かずに起動する。TDD なら Green（リファクタリングをするならそのあと）。自動で起動したときは `--eval-only` と同じく、評価・分類・レポートだけを行い、テストは足さない。強化と再実行は時間がかかるので、ユーザーが `/mutation-check` で頼んだときだけ行う
- 起動しない: 開発用ツール・skill・CI のスクリプト・インフラ設定のテスト、テストを変えていない変更
- 手動: `/mutation-check` で呼ばれたら、評価から強化・再実行まで行う。上の対象外のコードにも使う

## 引数

- `--base <ref>`: 比較元の git の ref（ブランチ・SHA・`<sha>^` など）。省略時は、PR があればその base、無ければリポジトリの規約（CLAUDE.md / AGENTS.md / memory）、それも無ければ `gh repo view --json defaultBranchRef`。gh が使えなければ `git symbolic-ref refs/remotes/origin/HEAD` が指すブランチ
- `--pkg <dir>`: Stryker を動かすディレクトリ（`package.json` のある所）。省略時は差分の TS/JS ファイルから一番近い `package.json` の場所を選ぶ。複数あれば pkg ごとに分けて実行する
- `--tests <path>...`: 評価するテストファイル。省略時は差分に含まれるテストファイル
- `--eval-only`: 評価とレポートだけを行い、テストを足さない
- `--manual`: TS/JS でも手動モードを使う
- `--threshold N`: スコアの目標値。指定されたら、達するまで強化と再実行を回す。指定が無ければ数値目標は置かない

## 手順

### 0. 前提

- 未コミットの変更があってもよい。`ranges` は未コミットの変更と新しいファイルを含めて範囲を出す。本番コードは変えず、手動モードで入れた変異はバックアップから書き戻す
- 作業ディレクトリ（以下 `<workdir>`）を作る。セッションの scratchpad があればその下の `mutation-check/<YYYYMMDD-HHMMSS>/`、無ければ `mktemp -d`。Stryker の設定・結果・記録はここに置き、対象のリポジトリには置かない
- レポートは `/tmp/mutation-check-<repo>-<branch>.html`（ブランチ名の `/` は `-` にする）

### 1. 範囲を決める

```bash
python3 <skill dir>/scripts/mutation_check.py ranges --base <base> > <workdir>/ranges.json
```

- `production` が変異を入れる範囲（差分で変わった行）、`tests` が評価するテスト
- `tests` が空で `--tests` も無ければ、評価するテストが無いので止めてユーザーに伝える
- `stryker: true` の本番コード（TS/JS）は Stryker モード、それ以外の言語は手動モードで評価する。両方あれば両方を行う
- 範囲（ファイルと行範囲）と評価するテストをコンソールに 1〜2 行で示してから進む（確認は求めない）
- 再実行で比べるため、`ranges.json` を回ごとに `<workdir>/round-<N>.ranges.json` として残す。`<N>` はその回の番号で、1 回目は `round-1`

### 2. ベースラインを確かめる

評価するテストを、プロジェクトのいつもの方法で流す（例: `npx vitest run <files>`、`npx jest <files>`、`go test ./pkg/... -run <name>`）。落ちるテストがあれば止めて報告する。落ちる状態で変異を入れても、結果を読めない。

### 3. 変異を入れてテストを流す

- Stryker モード: [references/stryker.md](references/stryker.md) の手順で設定を作り、実行し、`summarize` で結果をまとめる
- 手動モード: [references/manual.md](references/manual.md) の手順で、変異を 1 つずつ入れて対象のテストを流す

RuntimeError や CompileError が出たら、それは評価の結果ではなく設定か環境の問題。原因を直してから進み、結果として報告しない（references/stryker.md「トラブル対応」）。

### 4. 生き残った変異を分類し、対処を決める

Survived と NoCoverage の変異を 1 つずつ、本番コードとテストを読んで、次の 4 つのどれかに分ける。

| 分類 | 見分け方 | 対処の基本 |
|------|------|------|
| 未到達 | 評価するテストのどれもその箇所を実行しない（NoCoverage） | その箇所を実行する例ベースのテストを足す |
| 検証の不足 | 箇所は実行されるが、変異で変わる結果（戻り値・副作用・例外）を確かめていない | 期待値を確かめるアサーションを足す |
| 入力の不足 | 仕様の中の入力に、元のコードと変異で結果が変わるものがあるのに、テストがその入力を使っていない（境界・形式・組み合わせ） | PBT の候補。性質を書いて入力の範囲を広げる（[references/pbt.md](references/pbt.md)） |
| 等価変異 | 仕様の中のどの入力でも、元のコードと変異の結果が変わらない | テストを足さない |

結果が変わる入力は仕様の中で探す。仕様は型・コメント・README・issue・呼び出し側のコード・既存のテスト名から読む。

- 関数自身が扱いを約束している入力（ガード・型・ドキュメント）は、呼び出し側が今は渡さない値でも仕様の中
- 不正な形式、型が許さない値、仕様が扱うと決めていない種類の入力は仕様の外
- 結果の違いは、仕様が区別するものだけを数える。`0` と `-0` のように呼び出し側が区別しない違いは数えない。出力の形式（文字列・パス）は、仕様か既存のテストが形式を決めていれば違いを数える

対処は次のどれかに決める。

- テストを足す: 手順 5 へ
- 等価: 等価変異で、仕様の外の入力でも結果が変わらないとき。変わらない理由を書く
- 許容: テストを足さない。理由を書き、レポートでユーザーが確かめられるようにする。許容にしてよいのは次の 3 つ
  - 等価変異のうち、仕様の外の入力でだけ結果が変わるもの
  - ログの文言のように、仕様が決めていない箇所
  - DOM の配線や起動処理のように、プロジェクトが単体テストを書かない層。既存のテストがその層のファイルを 1 つも import しておらず、プロジェクトの方針（AGENTS.md・CLAUDE.md・README）にそれと食い違う記述が無ければ、そう読んでよい
- 保留: 結果が変わる仕様の中の入力が、どれも変異のほうが仕様に合うとき（元のコードがバグ）。元のコードが仕様に合い、変異が誤る入力が別にあれば、保留にせずその入力でテストを足す

元のコードが仕様に合わない結果を返す入力を見つけたら、変異と関係なくても、本番コードを直さずにバグ候補として記録して続ける。バグの振る舞いを固定するテストは書かない。バグ候補はレポートの要点のすぐ下に出し、直すかどうかをユーザーに聞く。

分類・対処・バグ候補を `<workdir>/triage.json` に書く。

```json
{
  "mutants": [
    {"id": "12", "file": "public/lib/monthlyProgress.js", "line": 22, "column": 7,
     "mutator": "EqualityOperator", "replacement": "value < 0",
     "category": "入力の不足", "resolution": "テストを足す",
     "reason": "負の日数をテストが使っていない", "distinguishing_input": "value = -1",
     "final": "Killed"}
  ],
  "bugs": [
    {"input": "origin = https://user:tok@github.com/acme/widget.git",
     "actual": "tok@github.com/acme/widget", "expected": "acme/widget",
     "related_mutants": ["17"]}
  ]
}
```

- 生き残りが 0 個なら `{"mutants": [], "bugs": []}` を書く
- `id` は Stryker の変異 ID か、手動モードの `manual-mutants.json` の ID
- `category` は上の表の 4 つの分類名のどれか。`distinguishing_input` は、結果が変わる入力が無ければ `null`（等価）、仕様の外の入力でだけ変わるならその入力（許容）
- `replacement` は Stryker の値をそのまま書く。手動モードは `after` を書き、`column` は `null`、`mutator` は references/manual.md の表の「対象」
- `final` は再実行のあとの結果（`Killed`・`Timeout`・`Survived`。手動モードも先頭を大文字にそろえる）か、`等価`・`許容`・`保留`・`残った`

`--eval-only` のとき（自動で起動したときを含む）は、分類と対処を書いたら手順 7 に進む。

### 5. テストを足す

対処を「テストを足す」にした変異のために、評価したテストファイルにテストを足す。新しいテストファイルを作ってもよい（次の再実行で範囲に入る）。

- 入力の不足は PBT を優先する（[references/pbt.md](references/pbt.md)）。PBT のライブラリがリポジトリに無ければ、どの変異のために要るかを示して、足してよいかをユーザーに聞く。断られたら、境界の値を並べた例ベースのテストにする
- その言語に定番の PBT ライブラリが無いとき（シェルなど）や、別の言語のテストを持ち込むことになるときは、聞かずに例ベースのテストにする
- テストは仕様から書く。テスト名と期待値は「この関数は何を約束しているか」で書き、変異の差分を写さない
- 足したテストを、変異を入れない本番コードで流す。落ちたら、テストの誤りか本番コードのバグかを仕様で確かめる。本番コードのバグなら、手順 4 のバグ候補として扱う

### 6. 同じ範囲で再実行する

手順 1 と 3 をやり直す（新しいテストファイルも範囲に入る）。手順 2 のベースラインは手順 5 で足したテストを流したことで済んでいる。手動モードは変異を書き出し直さず、既存の `manual-mutants.json` を使う（references/manual.md「強化と再実行」）。

- 本番コードの範囲が 1 回目と同じかを確かめる。差があれば、本番コードを変えていないかを見直す

  ```bash
  diff <(jq -S .production <workdir>/round-1.ranges.json) <(jq -S .production <workdir>/round-<N>.ranges.json)
  ```

- 1 回目と比べる。Stryker モードは `summarize <workdir>/round-<N>.json --before <workdir>/round-1.json`、手動モードは references/manual.md「強化と再実行」のとおり
- テストを足したのに検出できなかった変異があれば、手順 4 に戻って対処を決め直す。同じ変異に 2 回テストを足しても検出できなければ、それ以上は追わず、理由を書いて `final` を `残った` にする
- すべての変異の `final` が決まったら、手順 7 に進む
- `--threshold` があれば、目標に達するまで回す。等価変異があるために届かない目標なら、等価変異の数と届く上限を示して止める

### 7. レポートを出す

`/tmp/mutation-check-<repo>-<branch>.html` を html-report skill の手順で書き、`open` で開く。文章は AGENTS.md の「成果物の文章チェック」に従う。

- 対象: リポジトリ・ブランチ・base・merge-base と HEAD の SHA・モード（Stryker / 簡易）・変異を入れた範囲・評価に使ったテスト
- 要点: 変異の数、生き残りの数（1 回目 → 最後）、スコア（Stryker モードだけ）、足したテストの数、本番コードのバグ候補の有無
- 本番コードのバグ候補（あれば要点のすぐ下）: 入力・今の結果・仕様から期待する結果と、ユーザーに決めてほしいこと
- 生き残った変異の表: 場所、変異の中身（元 → 変異）、分類、対処、最後の結果
- 足したテスト: ファイル・テスト名・例ベースか PBT か・確かめている仕様
- 等価・許容とした変異と、その理由
- 確かめてほしいこと: 単体テストを書かない層と読んだ箇所、仕様の範囲として読んだこと、ユーザーに聞いたこと
- 残った課題: 検出できなかった変異、評価できなかった範囲（別の pkg、未対応の言語）
- 実行したコマンドと Stryker のバージョン、`<workdir>` の場所
- 手動モードの結果には「簡易」と付け、スコアは出さない

コンソールにはレポートのパスと、1 行の要約（例: 「生き残り 6 → 0、PBT 1 本と例ベース 2 本を追加」）を出す。評価だけのときは、対処を「テストを足す」にした変異の数と、`/mutation-check` で強化できることを添える（例: 「生き残り 6、うちテストを足す候補 4。`/mutation-check` で強化できます」）。候補が 0 個なら、強化の案内は付けない。このスキルの中では commit しない。足したテストは呼び出し元の作業（実装の commit など）の変更として扱う。

## 不正防止のルール

- 変異を検出するために本番コードを変えない
- `// Stryker disable` などのコメントや、`mutate` の除外・`ignorePatterns` の追加で、変異を評価の外に出さない
- 変異の差分を写したテストを書かない（正規表現の文字列そのものを比べる、変異で変わる定数を import して期待値にする、など）
- PBT で、テスト対象と同じ計算を書き写して期待値にしない
- 評価するテストの範囲を、スコアが上がる方向に後から変えない（既存のテストを評価に足すなど）。手順 5 で足したテスト（新しいファイルや関数）を評価に含めるのは、範囲の変更に当たらない。範囲を変えるときはユーザーに聞く
- 等価変異・許容とした変異は、すべて理由と一緒にレポートに出す

## やらないこと

- 本番コードを変える
- Stryker を devDependency に足す、Stryker の設定ファイルを対象のリポジトリに置く
- ユーザーの承認なしに PBT のライブラリを足す。PBT の無いリポジトリに初めて持ち込むときは、標準ライブラリ（Go の `testing/quick` など）でも先に聞く
- このスキルの中で commit・push する

## スクリプト

| コマンド | 役割 |
|------|------|
| `mutation_check.py ranges` | base との差分（未コミット・新規ファイルを含む）から、変異を入れる行範囲と評価するテストを JSON で出す |
| `mutation_check.py stryker-config` | Stryker の設定ファイルを `<workdir>` に書き、インストールと実行のコマンドを出す |
| `mutation_check.py summarize` | Stryker の `mutation.json` を集計し、生き残った変異とエラーを一覧にする。`--before` で前の回と比べる |
| `test_mutation_check.py` | 上の回帰テスト。`python3 -B -m unittest -v test_mutation_check.py`（scripts で実行） |
