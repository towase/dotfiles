# 終了案件のローカル環境整理

ユーザーが `$clean-project-local-data` と明示的に指定した場合に限り、この skill を使用する。明示指定がなければ、依頼内容が対象と一致または類似していても使用しない。

調査と削除を必ず別ターンに分ける。最初のターンは読み取り専用の調査と削除計画の提示だけを行い、ユーザーが項目を承認した後に限り実行する。

## 安全境界

- 案件との関連が明確なものだけを対象にする。対象外・共有物・判断不能なものは変更しない。
- 対象パス、リソース名、アカウント、プロファイルを完全修飾し、glob、未解決の変数、名前の部分一致を削除対象に使わない。
- `/`、ホームディレクトリ、範囲が曖昧な上位ディレクトリを対象として受け付けない。対象パスが不明なら調査前に確認する。
- シンボリックリンクをたどって対象外へ出ない。別ファイルシステムや対象外ディレクトリへ探索を広げない。
- `sudo`、`rm -rf`、全体 prune、キーチェーンや共有設定の一括削除など、広範囲・不可逆な操作を使わない。
- Git 履歴、コード、顧客データ、資格情報をネットワーク、外部 API、Web 検索、外部サービスへ送信しない。調査中はネットワークアクセスを伴うコマンドも避ける。
- 秘密値やファイル本文をツール出力・レポートへ出さない。必要最小限のローカル解析だけを行い、出力はパス、種類、サイズ、更新日時、権限、件数、キー名・セクション名に限定する。

## 1. 対象を確定する

1. 指定パスを絶対パス・物理パスへ解決し、存在、所有者、種類を確認する。
2. 対象が単一リポジトリか複数案件を含む親ディレクトリかを判定する。後者で範囲を一意に絞れなければユーザーに確認する。
3. 内容を表示せず、次の非秘密情報から案件の識別子を作る。
   - ディレクトリ名、Git remote のホスト・owner・repository（URL 内の資格情報は必ず伏せる）
   - Compose project 名・ラベル、サービス名、設定ファイル名
   - 組織名、案件名、固有ドメイン、プロファイル名、SSH Host alias
4. 対象ディレクトリ外の項目を「案件専用」とするには、原則として独立した根拠を 2 つ以上求める。完全一致するマウント元や Compose ラベルなどの強い根拠が 1 つある場合は、その旨を明記する。名前の類似だけなら「確認が必要」にする。

## 2. 読み取り専用で調査する

実行前に、各コマンドが状態を変更しないことと、秘密値を標準出力へ出さないことを確認する。専用 CLI が読み取り時にも設定更新やネットワーク通信を行う可能性があれば使わず、ファイルのメタデータ確認か手動確認へ回す。

### ファイルと Git

- 対象と同じ限定された親ディレクトリ内で、Git リポジトリ、複製、worktree、一時・検証用ディレクトリを探す。ホーム全体やディスク全体は走査しない。
- `.env*`、鍵・証明書、Terraform state、DB dump、CSV/JSON/log、顧客・本番データらしい名前、スクリーンショット、仕様書、議事録、IDE/workspace 設定をファイル名とメタデータで棚卸しする。
- `node_modules`、ビルド成果物、案件固有キャッシュ、一時ファイルも数と容量を確認する。共有 package cache 全体は候補にしない。
- Git の変更、未追跡ファイル、ローカルブランチ、upstream に対するローカル差分を確認する。remote の最新状態はネットワークなしでは保証できないと明記する。
- 秘密らしいファイルは本文を開かない。必要な識別はキー名のみを値なしで抽出し、値を表示しうる `cat`、無加工の `rg`、`env` などを使わない。

### Docker とローカルサービス

- コンテナ、イメージ、ボリューム、ネットワーク、Compose project を名前、ID、ラベル、マウント元、依存関係から照合する。
- PostgreSQL、MySQL、Redis、LocalStack、MinIO、DynamoDB Local、Firebase Emulator、および案件設定から判明したサービスを確認する。
- DB 名、接続先、保持場所は確認してよいが、テーブルやレコードなど業務データの内容は照会しない。
- 共有コンテナ、共有 DB server、外部 volume、複数 project から参照されるリソースは削除対象外にする。DB・volume は案件専用である根拠を必ず示す。

### 認証情報・開発ツール

- Git/GitHub CLI、AWS、Google Cloud、Kubernetes、npm/GitHub Packages、Docker Registry、Terraform、VPN、SSH を確認する。
- `.npmrc`、`.netrc`、`~/.aws`、`~/.config/gcloud`、`~/.kube`、`~/.ssh/config`、`~/.docker/config.json` は、存在・権限・更新日時と、値を除いた host/profile/context/registry/key 名だけを確認する。
- credential helper から秘密を取得しない。`security ... -w`、キーチェーン全体の dump、秘密を表示する auth/token コマンドを使わない。
- SSH は設定、鍵ファイルの fingerprint、`ssh-agent` の fingerprint、案件固有証明書を照合する。秘密鍵本文や公開鍵本文は表示しない。
- macOS キーチェーンは service と account を完全一致で絞れる場合だけ CLI でメタデータを確認し、それ以外は Keychain Access での手動確認にする。
- VS Code、JetBrains、Postman、Bruno、Insomnia、TablePlus、DBeaver、DataGrip は、安全に読める設定の存在と案件識別子だけを確認する。独自 DB、暗号化ストレージ、同期設定が必要ならアプリ上の手順を示す。

### 履歴・OS 状態

- シェル履歴は、案件パス・識別子と token/secret/password 等の入力痕跡をローカルで検査する。該当行の本文や秘密値は出さず、履歴ファイル、行番号、検出カテゴリ、件数だけを報告する。
- macOS の「最近使った項目」など、安全に限定・自動変更できない OS 状態は手動確認へ回す。

## 3. 削除計画を提示して停止する

各対象に一意な ID を付け、根拠を添えて次の 7 見出しをそのまま使用する。ファイル、Docker、認証情報などの調査領域別見出しへ置き換えない。

1. **確実に削除してよいもの**: 案件専用の根拠が十分で、共有・未退避データ・ローカルのみの Git 変更がないもの
2. **案件専用と思われるが確認が必要なもの**: 根拠不足、未コミット/未追跡データ、顧客データ、共有可能性などがあるもの。確認方法も記す
3. **削除しないもの**: 個人用・別案件・共有と判断したもの、およびその根拠
4. **手動確認が必要なもの**: ターミナルから安全に確認できない項目と、アプリ内の具体的な確認手順
5. **削除の影響**: 復元可否、再認証・再取得・再構築の必要性、依存先への影響
6. **実行予定コマンド**: ID ごとに、展開済みの正確な対象を使うコマンド。placeholder や資格情報を埋め込まない。ゴミ箱へ移す場合も、既存項目と衝突しない完全な移動先を事前確認して示す
7. **削除後の確認方法**: 元パス、Docker/DB 状態、設定参照、agent 登録、履歴痕跡などの読み取り専用確認

パスまたはリソース名、種類・サイズ・更新日時、案件との関連根拠を可能な範囲で併記する。「候補なし」「未調査」も省略せず理由を書く。この報告を提示したら、削除や設定変更を一切行わず承認を待つ。最初の依頼に「削除して」と含まれていても、この承認ゲートを省略しない。

完全な識別子や安全な編集方法が不足し、実行コマンドを正確に書けない項目は推測しない。「未確定」として不足情報、その読み取り専用の確認方法、手動確認が必要な理由を示す。正確なコマンドを再提示するまでは、その項目を承認・実行可能な候補として扱わない。

## 4. 承認された対象だけを整理する

- 承認は報告 ID または完全な対象名で受ける。承認範囲が曖昧なら実行しない。
- 実行直前に ID、パス/リソース ID、案件専用の根拠、依存関係が変わっていないか再確認する。差異や新しい対象が見つかったら停止し、改めて報告する。
- ファイルとディレクトリは、利用可能なら明示パスを macOS のゴミ箱へ移す方法を優先する。永続削除はユーザーがその正確なコマンドを明示承認した場合だけ行う。
- Docker は承認された container/image/volume/network または根拠を確認済みの Compose project だけを ID・完全名で削除する。`docker system prune`、全 volume 削除、曖昧な一括指定は使わない。
- DB、資格情報、SSH 設定、キーチェーン項目は database/profile/host/service/account を完全指定する。共有設定ファイル自体を削除せず、承認された entry だけを編集する。
- 1 項目ずつ実行して結果を記録する。1 件の失敗を理由に対象範囲を広げたり、強制オプションへ切り替えたりしない。

## 5. 事後確認を報告する

調査時と同じ読み取り専用チェックを再実行し、次を報告する。

- 実際に整理した対象と実行結果
- 整理しなかった対象と理由
- エラー、状態変化、未確認事項
- 手動対応が必要な作業（ゴミ箱を空にする場合を含む）
- 案件由来のファイル、リソース、設定、資格情報が残っていないかの確認結果

残存物を見つけても追加削除せず、新しい候補として根拠・影響・コマンドを提示し、再承認を待つ。
